# ADR 0013: Kubernetes manifests and the local kind overlay

- Status: accepted
- Date: 2026-09-30

## Context

Spec section 12 asks for a kustomize base with the three services, a local overlay that also runs MySQL, MongoDB, Kafka and SFTP without operators, the API exposed by `NodePort` or `kubectl port-forward` (documented), and `scripts/k8s-up.sh` verified on kind or minikube. The same repository already runs the whole system in Docker Compose, with init scripts in `docker/` for the MySQL schemas and users, the MongoDB audit user and indexes, and the Kafka topics. The local machine is Windows 11 with Docker Desktop; the scripts run in Git Bash.

## Decision

**Cluster: kind.** One control-plane node named `remit` (`k8s/kind-config.yaml`). kind runs inside the Docker Desktop VM that already holds the images, needs no hypervisor, and `kind load docker-image` copies the locally built `remit/<service>:latest` images into the node, so no registry is involved. The deployments use `imagePullPolicy: IfNotPresent` for that reason. With Docker Desktop's containerd image store kind cannot tell that an image is already on the node, so `k8s-up.sh` records each loaded Docker image ID as an annotation on the node: an unchanged ID skips the copy (about 15 s per image), a new one is loaded and its deployment restarted, because the tag stays `latest`. The node image is pinned by digest in the kind config.

**Exposure: NodePort.** The local overlay patches `api-service` to `NodePort` 30080, and the kind config maps node port 30080 to `127.0.0.1:8080` on the host. The API then answers at `http://localhost:8080`, the same address as compose, so the smoke test, Newman and the runbook commands work unchanged, and nothing has to stay running in a terminal. `kubectl -n remit port-forward svc/api-service 8080:8080` is the documented alternative (for a cluster created without the mapping). An Ingress controller was not added: one more component to install for a single HTTP service.

**Base versus overlay.** `k8s/base` holds only what a real environment would deploy: the namespace, the three Deployments and ClusterIP Services, a PodDisruptionBudget for routing-service (2 replicas), and the shared `remit-config` ConfigMap with production-like values (30 s SFTP poll, real business date, chaos hook off, no seeded users). The Secret `remit-secrets` is never committed; `k8s/base/secret.example.yaml` documents its keys and `scripts/k8s-secrets.sh` builds it from `.env`. `k8s/overlays/local` adds the infrastructure (`infra/`), the NodePort patch, and a ConfigMap patch with the compose demo values: 10 s poll, business date 2026-10-15 (ADR 0005), the `FORCE_FAIL` chaos hook on and seeded operator and admin users. The chaos switch is set with `REMIT_ROUTING_CHAOSENABLED`, Spring's environment form of `remit.routing.chaos-enabled`, so the `k8s` profile in `application.yml` keeps it off and no Java or YAML of the services changed.

**Infrastructure: plain StatefulSets and Deployments, no operators.** MySQL 8.4, MongoDB 7 and Kafka 3.9 (single KRaft node, advertised as `kafka:9092`) are one-replica StatefulSets with small PersistentVolumeClaims from kind's default `standard` StorageClass (local-path). SFTP (atmoz/sftp) is a Deployment with its own PVC and the `Recreate` strategy. PVCs rather than `emptyDir` so a pod restart keeps the data (a failed batch job needs its file in `/processing`, and the read model and audit trail should survive a MySQL or MongoDB restart); they are deleted with the namespace or the cluster. The topics are created by a `kafka-init` Job.

**One copy of each init script.** The overlay turns `docker/mysql/init.sql`, `docker/mysql/init-users.sh`, `docker/mongo/init.js` and `docker/kafka/create-topics.sh` into ConfigMaps with `configMapGenerator`, mounted into `/docker-entrypoint-initdb.d` and the Job. Because those files sit outside the kustomization root, the overlay is rendered with `kubectl kustomize --load-restrictor LoadRestrictionsNone`; a plain `kubectl apply -k` refuses it with a clear error. Copies under `k8s/` would work with `apply -k` but could drift from what compose runs.

**Start order without crash loops.** Each service has an init container, running the service's own image (bash, no extra image), that waits until its dependencies accept TCP connections. A ClusterIP Service only forwards to ready pods, so this also waits for the infrastructure readiness probes (MySQL and MongoDB only become ready after their init scripts ran). A startup probe then gives Spring Boot up to 200 s on one CPU before liveness and readiness start.

**Security.** The service pods meet the `restricted` Pod Security Standard: uid 10001, `runAsNonRoot`, read-only root file system with `emptyDir` volumes for `/tmp` and intake's `/staging`, no privilege escalation, all capabilities dropped, `RuntimeDefault` seccomp, no service account token, only the Secret keys each service needs. MySQL, MongoDB, Kafka and the Job run as their images' non-root users with the same restrictions except the read-only root file system. SFTP cannot: sshd starts as root to chroot the user. The namespace therefore enforces `baseline` and warns on `restricted`, which flags exactly that one pod. `enableServiceLinks: false` everywhere, because the Kafka image turns every `KAFKA_*` variable into a broker setting and service links would inject `KAFKA_PORT=tcp://...`.

## Consequences

- `scripts/k8s-up.sh` is the supported entry point; it creates the cluster, loads the images, applies the Secret and the overlay and waits for everything. Rerunning it is safe.
- The samples are accepted once per database (duplicate file detection). The smoke test against kind needs an empty stack: `scripts/k8s-down.sh --keep-cluster` then `scripts/k8s-up.sh` resets the data but keeps the cluster and its images.
- ConfigMap and Secret values are read at pod start only. After a change: `kubectl -n remit rollout restart deployment` (or `scripts/k8s-secrets.sh --restart`). Database passwords in the Secret are only applied by the init scripts on an empty volume.
- kind's containerd gives containers an open files limit of about a billion. OpenSSH in the SFTP pod then spends seconds closing descriptors at the start of every session and the SFTP handshake times out, so the pod lowers the limit to 65536 before starting sshd. The JVM services are not affected.
- The MySQL durability trade-off of ADR 0011 (`innodb_flush_log_at_trx_commit=2`, `sync_binlog=0`) applies to the local overlay too, for the same reason.
- Moving to a real cluster means replacing `overlays/local` with an overlay that points at managed MySQL, MongoDB, Kafka and SFTP (or operators), pushes the images to a registry and exposes the API through an Ingress; the base stays as it is.
